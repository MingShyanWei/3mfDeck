### 3.1b 修訂：3MF 以 ZIP 內容判定重複（M36）

**問題（2026-10-13 以使用者真實檔案櫃唯讀查詢）**：櫃中 141 筆記錄都已建立指紋，「重複」篩選卻是 0 組。
當初列為疑似重複的兩組（M33 背景）其實**內容完全相同**，只是 ZIP 打包時間不同：

| 檔案 | 整檔 SHA-256 | ZIP 內各檔（名稱＋CRC） | 打包時間 |
|---|---|---|---|
| `Fast NO FUZZY-U1.3mf` ／ `2026/Fast NO FUZZY-U1.3mf` | 不同（979d5c… ／ 3358ee…） | 23 個全部相同 | 2026-09-29 13:47 ／ 2026-10-06 15:00 |
| `Filament+Swatch+Sample+Card-U1.3mf` ／ `色卡/…` | 不同（1c540a… ／ 65e6c2…） | 25 個全部相同 | 2026-09-28 06:01 ／ 2026-09-23 16:04 |

3MF 是 ZIP；同一份內容在不同時間轉 U1、或被切片軟體原封不動重存，ZIP 會記下新的打包時間，整檔位元組就不同。
M33 定義「整檔 SHA-256 相同才算重複」，因此照規格判定為不重複——規則太嚴，抓不到使用者真正要抓的情況。

- **新的重複定義**：
  - **ZIP 格式的檔案**（3MF；檔頭為 ZIP 簽章 `PK\x03\x04` 的任何檔案）：指紋＝ZIP 內**每個檔案**的
    「名稱、CRC-32、未壓縮大小」依名稱排序後串成清單的 SHA-256。**不含**打包時間、壓縮方式、壓縮後大小、目錄項目（名稱以 `/` 結尾）、ZIP 註解。
    → 內容相同、只差打包時間或壓縮程度的檔案算重複；任何一個內部檔案內容不同（改設定、改模型、換縮圖、轉不同噴嘴）就不算。
  - **其他格式**（STL、OBJ、GLB、STEP…）：照舊整檔 SHA-256。
  - ZIP 讀取失敗（損毀、非標準）→ 退回整檔 SHA-256。
  - 讀法：只讀 ZIP 尾端的中央目錄（含 ZIP64），不解壓、不讀整檔；大檔（如 186 MB 的 3MF）也只讀幾 KB。
- **指紋版本**：ZIP 內容指紋存為 `zip1:<sha256 hex>`，與整檔指紋（純 64 位 hex）分開，兩種永遠不會互相比對成重複。
- **舊資料**：App 啟動後的背景補指紋（3.1b 既有機制）同時重算「ZIP 格式但仍是整檔指紋」的記錄；
  iCloud 尚未下載到本機的檔案照舊略過（`SF_DATALESS`），下載後再算。完成前「重複」篩選照舊顯示「尚有 N 個檔案未建立指紋」。
- **匯入、重新定位、從回收桶還原**：一律改用新指紋（3.1b 既有流程不變，只換指紋的算法）。
- **不變**：「重複」篩選分組、不自動刪除、回收桶不列入、重複不匯入等 3.1b 規則全部照舊。
- **風險**：不同內容的兩個 ZIP 檔要「每個內部檔的名稱、大小、CRC-32 全部相同」才會被誤判，實務上幾乎不可能；
  且 App 只列出重複組、不自動刪除，最後由使用者決定。
- **離線**：全部本機計算，不連網。

**驗收**
- 使用者檔案櫃：重算完成後「重複」篩選列出上面兩組（`Fast NO FUZZY-U1`、`Filament+Swatch+Sample+Card-U1`），
  且列出的每一組都經逐項比對 ZIP 內檔案確認內容相同；記錄重算前後的組數與 186 MB 檔案的指紋時間。
- 單元測試：同一份內容以不同打包時間／壓縮程度重新打包 → 指紋相同；改一個內部檔的一個位元組 → 不同；
  目錄項目有無不影響；STL 等非 ZIP 照舊；損毀 ZIP 退回整檔 SHA-256；ZIP64；舊整檔指紋的 3MF 在背景補算時被重算。
- 匯入：內容相同、打包時間不同的 3MF 匯入時被略過並提示既有記錄（3.1b 匯入規則）。
- 既有測試全數通過；smoke 的 M33 步驟照舊通過。

**待確認（建議值已寫入上文）**

2. 適用範圍是「檔頭為 ZIP 的任何檔案」而不只副檔名 `.3mf`（例如壓縮過的 AMF 也是 ZIP）——建議依檔頭判斷。
